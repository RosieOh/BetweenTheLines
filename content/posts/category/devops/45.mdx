# [AetherDesk] 같은 브리지에 있으면 인증은 없는 것과 같다

브라우저에서 리눅스 데스크톱을 쓰는 SaaS를 만들었습니다.
사용자마다 KDE 컨테이너를 띄우고, VNC를 웹소켓으로 감싸 브라우저에 물리는 구조입니다.

```
Xvfb → dbus → KDE Plasma → x11vnc(:5901) → websockify/noVNC(:6080)
```

인가는 Traefik의 **ForwardAuth**로 처리했습니다.
요청이 프록시를 지날 때 백엔드에 물어보고, 남의 데스크톱이면 403을 주는 방식입니다.

깔끔하다고 생각했습니다. 그러다 이 질문을 받았습니다.

> "noVNC 화면 비밀번호 이거 없어야되지 않아?"

ForwardAuth가 이미 막고 있으니 VNC 자체 비밀번호는 중복 아니냐는 얘기였습니다.
확인해보고 지우려다가, 실제로 뚫어보기로 했습니다.

## 💀 발견 — 컨테이너 안에서는 프록시를 안 거친다

테넌트 A의 데스크톱 컨테이너 안에서 터미널을 열고, 테넌트 B를 직접 불렀습니다.

```bash
curl http://aether-desk-tenantB:6080/vnc.html
# HTTP 200

curl -H 'Upgrade: websocket' ... http://aether-desk-tenantB:6080/websockify
# HTTP 101   ← 남의 화면에 그대로 연결됨
```

**101입니다.** 웹소켓 핸드셰이크가 성립했습니다.
테넌트 A가 테넌트 B의 화면을 그대로 볼 수 있었습니다.

원인은 한 문장으로 정리됩니다.

> **ForwardAuth는 Traefik을 *지나는* 트래픽만 검사한다.**
> 같은 브리지 네트워크에 있는 컨테이너끼리는 프록시를 거치지 않으니 인가가 없는 것과 같다.

모든 데스크톱이 공용 `aether_edge` 네트워크에 있었습니다.
Docker의 내장 DNS가 컨테이너 이름을 해석해주니, 옆 컨테이너로 바로 갈 수 있었습니다.

그리고 그 순간 **VNC 비밀번호가 유일한 방어선**이었습니다.
그걸 "중복이니까" 지웠으면 크로스테넌트 화면 탈취가 열렸을 겁니다.

## 🛠️ 해결 — 세션마다 네트워크를 판다

공용 브리지를 버리고 **세션마다 전용 네트워크**를 만들었습니다.

```
aether-net-{slug}    ← 데스크톱 + Traefik 둘만 참여
```

멤버가 둘뿐이니 옆 데스크톱이 아예 보이지 않습니다.

검증 결과입니다.

| 시도 | 결과 |
| --- | --- |
| 타 컨테이너 → 데스크톱 (이름으로) | DNS 해석 실패 |
| 타 컨테이너 → 데스크톱 (IP 직접) | 타임아웃 (`DOCKER-ISOLATION-STAGE-*`) |
| Traefik 경유 | vnc.html 200 / rfb.js 200 / websockify **101** |

전체 네트워크 구성은 이렇게 정리됐습니다.

```
aether_edge        Traefik · Backend · Frontend
aether_backplane   internal: true — Traefik · Backend · Postgres · Prometheus (외부 노출 0)
aether-net-{slug}  데스크톱 + Traefik (세션당 1개)
```

`internal: true`가 붙은 backplane에는 DB가 들어갑니다. 외부로 나가는 경로 자체가 없습니다.

### ⚠️ 그런데 네트워크에는 상한이 있다

세션마다 네트워크를 파면 곧 벽에 부딪힙니다.

Docker 기본 주소 풀은 `172.17.0.0/12`를 `/16`으로 쪼개 씁니다.
**사용자 정의 네트워크를 16개 남짓밖에 못 만듭니다.**

```json
// daemon.json — 이거 없으면 17번째 세션부터 생성 실패
{ "default-address-pools": [{ "base": "10.200.0.0/12", "size": 24 }] }
```

그리고 고갈을 삼키지 않고 명시적 에러로 바꿨습니다.

```
503 NETWORK_POOL_EXHAUSTED
```

"컨테이너 생성 실패"라는 뭉뚱그린 500보다, 무엇이 부족한지 말해주는 게 낫습니다.

## 🧹 세션 회수 — 리퍼를 18번 고친 이유

띄운 컨테이너는 회수해야 합니다. `SessionReaper`를 만들었고, 이 파일을 **18번** 고쳤습니다.
(같은 세션에서 `DesktopService`가 45회로 1위, 리퍼가 3위였습니다.)

회수 대상은 다섯 종류입니다.

| 종류 | 조건 |
| --- | --- |
| IDLE | 일정 시간 heartbeat 없음 |
| GHOST | DB엔 RUNNING인데 컨테이너가 없음 |
| ORPHAN | 컨테이너는 있는데 DB에 없음 |
| STUCK | PROVISIONING에서 안 넘어감 |
| OVERDUE | 플랜의 최대 세션 시간 초과 |

### 판정 기준 — 유휴를 무엇으로 재나

처음엔 ForwardAuth 히트로 `last_seen_at`을 갱신했습니다. 그런데 이게 틀렸습니다.

> **웹소켓이 한 번 연결되면 이후 VNC 프레임은 프록시를 재통과하지 않습니다.**

즉 화면을 열심히 보고 있는 사용자일수록 ForwardAuth 히트가 **0**입니다.
가장 활발한 사용자를 유휴로 판정하고 죽이는 구조였습니다.

뷰어가 탭이 보이는 동안 60초마다 heartbeat를 보내도록 바꿨습니다.

```
POST /api/desktop/heartbeat
```

### 오탐 — 가장 위험한 오작동

회수 루프에서 제일 무서운 건 **정상 세션을 죽이는 것**입니다. 세 가지를 막았습니다.

**① 노드 장애를 GHOST로 오인하지 않기**

컨테이너 목록 조회에 실패한 노드는 GHOST 판정에서 아예 제외합니다.
노드가 잠깐 응답을 안 한다고 그 위의 모든 세션을 지우면 재앙입니다.

**② 생성 직후를 ORPHAN으로 오인하지 않기**

컨테이너를 만들고 DB에 커밋하기까지 짧은 창이 있습니다. 그 사이엔 "DB에 없는 컨테이너"입니다.
**120초 유예**를 뒀습니다.

**③ 멀티노드 불변식**

두 노드가 같은 Docker 엔진을 가리키면 한쪽 컨테이너가 다른 쪽 목록에도 나타납니다.
그럼 GHOST/ORPHAN 오판이 납니다. **"노드 하나 = 엔진 하나"** 를 불변식으로 문서에 못박았습니다.

### 경합 — 백엔드가 여러 대일 때

리퍼가 여러 인스턴스에서 동시에 돌면 안 됩니다. Postgres 어드바이저리 락으로 리더를 뽑습니다.

```ts
pg_try_advisory_xact_lock(0x41455448)   // 'AETH'
```

그리고 이전 사이클이 아직 도는 중이면 건너뜁니다.

```ts
if (this.running) return;
```

### 고아 네트워크는 위생 문제가 아니라 가용성 문제

`reapOrphanNetworks`를 나중에 추가했는데, 이게 생각보다 중요했습니다.

세션이 사라져도 네트워크가 남으면 **주소 풀이 고갈되어 새 세션 생성이 통째로 막힙니다.**
"지저분하다" 수준이 아니라 서비스가 멈춥니다.

순서도 중요했습니다. **반드시 마지막 단계**여야 합니다.
앞 단계가 컨테이너를 먼저 없애야 네트워크를 지울 수 있으니까요.

## 🐛 리퍼를 통째로 죽인 한 줄

E2E 테스트가 잡아준 버그가 있습니다.

```sql
-- 유휴 경고 대상 조회
WHERE ... ($1 - $2) ...
```

두 파라미터가 모두 `unknown` 타입으로 넘어가 Postgres가 연산자를 결정하지 못했습니다.

```
operator is not unique
```

그런데 이게 단순한 쿼리 실패로 끝나지 않았습니다.
`reapIdle`이 **매 사이클 예외를 던지면서 그 뒤의 GHOST·네트워크·스토리지 회수가 전부 멈췄습니다.**

증상은 백엔드 로그에 60초마다 같은 에러가 찍히는 것뿐이었습니다.
`::int` 명시 캐스트로 해결했습니다.

> **타입체크로는 절대 안 잡히는, DB에 실제로 던져야만 보이는 회귀였습니다.**

이 경험이 E2E를 도입한 직접적 계기였습니다.
그날 버그를 7건 잡았는데 **타입체크나 SQL 스모크로 잡힌 건 0건**이었습니다. 전부 실제로 돌려야 나왔습니다.

## 🧪 E2E — 실물로만 보이는 것들

Playwright로 11개 스펙, 최종 **72 passed / 3 skipped**까지 갔습니다.
컨트롤플레인 헬스체크부터 크로스테넌트 격리, 파일 업다운, 백업·복원, 실제 브라우저에서 **RFB 픽셀이 흐르는지**까지 봅니다.

E2E가 아니면 못 잡았을 것들입니다.

**미들웨어 순서** — `StripPrefix`가 `ForwardAuth`보다 먼저 실행돼서,
인가 시점엔 경로가 이미 `/vnc.html`로 잘려 slug를 읽을 수 없었습니다.
**데스크톱 라우팅 전체가 죽어 있었습니다.** `chain → authz → strip`으로 고쳤습니다.

**SQL 42P08** — `$2`를 `status = $2`(varchar)와 `CASE WHEN $2 = 'RUNNING'`(text) 양쪽에 쓰다가
모든 상태 전이가 실패했습니다. 보상 트랜잭션도 리퍼 회수도 전부 막혔습니다.
SQL 스모크가 이걸 놓친 이유는 **파라미터 대신 리터럴을 인라인해서 테스트했기 때문**입니다.

**헬스체크 false positive** — x11vnc가 죽어도 websockify는 정적 HTML을 200으로 계속 서빙합니다.
"화면은 절대 안 뜨는데 healthy"인 상태였습니다.

그런데 이걸 고치려고 RFB 포트를 raw TCP로 찔렀더니 **x11vnc가 그걸 정상 클라이언트로 처리**해서
5초마다 핸드셰이크 에러를 뱉었습니다. 19분에 224건. 소켓을 안 건드리는 방법으로 다시 바꿨습니다.

## 🔒 하드닝에서 배운 것

컨테이너 제한은 이렇게 걸었습니다.

```ts
NanoCpus: cpuCores * 1e9
Memory / MemorySwap: 동일값        // 스왑 완전 차단 (시끄러운 이웃 방지)
MemoryReservation: Memory * 0.6
PidsLimit, ShmSize                 // Shm 없으면 KDE 즉사
CapDrop: ['ALL']
CapAdd: ['CHOWN','SETUID','SETGID','DAC_OVERRIDE']
```

Docker 소켓은 직접 마운트하지 않고 socket-proxy 두 개를 경유합니다.
Traefik용은 **POST를 아예 0**으로 막았습니다. 읽기만 하면 되니까요.

### seccomp 프로필이 인라인으로 안 들어간 이유

커스텀 seccomp 프로필을 만들어 `ptrace`, `bpf`, `perf_event_open` 등을 제거했습니다.
그런데 인라인 JSON으로 넘기니 컨테이너 생성이 400으로 거부됐습니다.

**12KB 인라인이 socket-proxy의 haproxy 버퍼를 넘겼기 때문**이었습니다.
호스트 경로 참조 방식으로 바꿔서 해결했습니다.

### `no-new-privileges` 하나가 검은 화면을 만들었다

다른 데스크톱 이미지를 붙였더니 **화면이 검게만 나왔습니다.**

가설을 차례로 기각했습니다. TLS, HTTP/2, 웹소켓 압축, Traefik 미들웨어 체인,
심지어 Traefik 자체까지 우회해봤는데 동일했습니다.

결정적 단서는 프레임 계측이었습니다.

```
프레임 개수:  직접 844  vs  프록시 840    ← 거의 같음
전송 바이트: 166,600B  vs   8,154B      ← 20배 차이
최대 프레임:  80,788B  vs   3,749B
10KB 넘는 프레임: 6개  vs      0개
```

**프레임은 오는데 내용이 없었습니다.** 화면 갱신이 실제로 없었던 겁니다.

범인은 `no-new-privileges: true`였습니다.
그 이미지는 기동 중 setuid 권한 상승이 필요한데 막히니
**컴포지터가 크래시-재기동 루프**에 빠져 있었습니다. 캡처할 데스크톱이 없으니 검은 화면이죠.

순정 이미지에 그 플래그 하나만 얹어서 재현했습니다.
결국 이 플래그는 **뷰어 방식이 noVNC인 경우로만 한정**했습니다.
나머지 방어(비루트 실행, CapDrop ALL, seccomp, 네트워크 격리, 리소스 제한)는 그대로 둡니다.

## 🙈 스스로 속은 순간

기록해둘 만한 게 하나 더 있습니다.

"데스크톱이 렌더링된다"며 스크린샷을 근거로 정상 판정을 내렸는데,
**그게 사실 잠금화면이었습니다.**

중앙의 큰 시계가 잠금화면 위젯이었고, Plasma 패널이 없다는 게 명백한 단서였는데
배경화면이 보인다는 것만으로 넘어갔습니다.

실제 원인은 이랬습니다.

> `useradd`로만 만든 계정은 `/etc/shadow`에 `devuser:!:` — **잠긴 상태**입니다.
> PAM 인증이 성공할 수 없으니, 한 번 잠기면 영원히 못 풉니다.

자동 잠금을 끄고, Kiosk 정책으로 잠금 액션 자체를 막고,
그래도 잠기면 풀 수 있도록 계정 비밀번호를 세션 시크릿과 맞췄습니다.
(그 값을 이미 아는 사람만 화면을 볼 수 있으므로 노출 표면은 늘지 않습니다.)

**"화면이 나온다"와 "데스크톱이 동작한다"는 다릅니다.** 스크린샷을 볼 때 무엇을 확인할지 정해두는 게 낫습니다.

## 📌 정리

- **프록시 단 인가는 프록시를 지나는 트래픽만 지킵니다.** 같은 네트워크의 이웃은 그냥 들어옵니다
- 멀티테넌시에서 **네트워크 격리는 선택이 아니라 기본**입니다. 세션당 네트워크가 가장 확실합니다
- 세션당 네트워크를 쓰면 **Docker 주소 풀 상한(기본 16개)에 걸립니다.** `default-address-pools`를 먼저 늘리세요
- 고아 네트워크는 위생이 아니라 **가용성 문제**입니다. 쌓이면 새 세션이 아예 안 만들어집니다
- **웹소켓은 한 번 연결되면 프록시를 재통과하지 않습니다.** 활동성 판정을 프록시 히트로 하면 정반대 결과가 나옵니다
- 회수 루프의 최대 리스크는 **정상 세션 삭제**입니다. 노드 장애·생성 직후·중복 엔진 세 가지를 먼저 막으세요
