# [Friday] 파이프라인이 자기 자신을 먹었다

[앞선 글](/post/41)에서 Claude Code 세션 로그에 주제를 붙이는 분류기를 만들었습니다.
로컬 `claude` CLI를 print 모드로 부르는 방식이었고, 잘 돌아갔습니다.

그리고 이걸 자동 실행으로 걸었습니다. 그 다음이 문제였습니다.

## 🕰️ 증상

수동으로 돌릴 때 1~2분이면 끝나던 `topics` 단계가 **15분이 지나도 안 끝났습니다.**

DB를 열어봤습니다.

```
사용자 세션:  72 → 176개
jsonl 파일:  169 → 410개
```

한 번의 자동 실행 만에 세션이 두 배 넘게 늘어 있었습니다.
그런데 저는 그 사이에 Claude Code를 쓴 적이 없었습니다.

## 🔍 원인 — 도구가 자기 입력을 만들고 있었다

파이프라인은 이렇게 생겼습니다.

```
extract.py   ~/.claude/projects/*.jsonl 파싱 → SQLite
topics.py    각 세션을 claude -p 로 분류
```

여기서 놓친 게 있습니다. **`claude -p`도 Claude Code 세션입니다.**
호출할 때마다 `~/.claude/projects/` 밑에 jsonl이 하나 생깁니다.

그러니 이렇게 됩니다.

```
topics.py 가 claude -p 를 80회 호출
   → 세션 jsonl 80개 생성
      → 다음 extract.py 가 그걸 "사용자 세션"으로 인식
         → 다음 topics.py 가 그 세션들의 주제를 추출하려고 claude -p 를 또 호출
            → 또 세션 생성
               → ...
```

**도구가 자기 출력을 자기 입력으로 먹고 있었습니다.**

수동 실행에서 안 보였던 이유는 단순합니다. 한 번 돌리고 끝냈으니까요.
자동 실행으로 주기가 생기자 루프가 완성됐습니다.

증가 추이는 이랬습니다.

```
jsonl:  169 → 297 → 410 → 420
세션:   72 → 176
```

## 💸 비용

`claude -p`는 응답 JSON 봉투에 `total_cost_usd`를 담아 줍니다. 호출당 **$0.087**였습니다.

자기가 만들어낸 세션이 230개. **API 환산 약 $20**입니다.
개인 도구에서 하룻밤에 20달러어치 무의미한 호출이 돌았다는 뜻이고,
방치했으면 기하급수로 늘었을 겁니다.

## ❌ 첫 시도 — 휴리스틱은 안 통했다

"도구가 만든 세션"을 식별하면 될 것 같았습니다.
레코드에 `entrypoint`, `userType` 같은 필드가 있으니 그걸로 구분하려 했습니다.

안 됐습니다.

> `claude -p` 자식 프로세스가 **부모의 값을 그대로 물려받아**
> 전부 `claude-vscode` / `external`로 찍힙니다.

제가 VS Code에서 파이프라인을 실행했으니, 그 안에서 태어난 세션도 전부 VS Code 세션으로 보였습니다.
**메타데이터만 봐서는 사람이 연 세션과 도구가 연 세션이 구분되지 않습니다.**

프롬프트 내용으로 판별하는 것도 생각했지만, 그건 휴리스틱이고 언젠가 오탐이 납니다.

## ✅ 해결 — 호출한 쪽이 id를 기록한다

정확한 방법은 다른 데 있었습니다.
`claude -p`가 `--output-format json`으로 돌려주는 봉투에 **`session_id`가 들어 있습니다.**

즉, **내가 방금 만든 세션의 id를 내가 알 수 있습니다.** 추측할 필요가 없습니다.

```python
def call_claude(prompt):
    result = subprocess.run([CLAUDE, "-p", ...], input=prompt, ...)
    envelope = json.loads(result.stdout)

    # 자기가 만든 세션 id를 즉시 기록한다.
    # 마지막에 몰아서 쓰지 않는 이유: 중간에 죽어도 id는 남아야 하기 때문
    record_spawned(envelope["session_id"])

    return envelope
```

`extract.py`는 `tool_session` 테이블에 있는 id를 건너뜁니다.
이미 새어 들어온 것은 삭제합니다.

포인트는 **기록 시점**입니다. 함수 끝이 아니라 응답 직후에 씁니다.
파이프라인이 중간에 죽으면 그 세션들은 DB에 안 남고, 다음 실행이 또 그걸 분류하게 되니까요.

## 🧹 이미 오염된 것 되돌리기

문제는 이미 들어온 230개였습니다. `session_id`를 기록하기 전에 생긴 것들이라 추적할 방법이 없었습니다.

`backfill_tool_sessions.py`를 따로 만들었습니다.
`topics.py`가 쓰는 **프롬프트 원문과 세션의 첫 발화를 대조**하는 방식입니다.

```
227개 후보 중 214개 매칭
남은 13개는 실제 사람이 연 세션
```

이 스크립트를 쓸 때 두 가지를 지켰습니다.

- **`--apply` 없이는 아무것도 쓰지 않는다** (기본이 dry-run)
- **`--since`로 날짜 범위를 좁힌다** — 오래된 진짜 세션을 건드릴 위험 제거

그리고 **jsonl 파일 자체는 지우지 않았습니다.**
DB에서 필터링하는 것으로 충분하고, 파일 삭제는 되돌릴 수 없기 때문입니다.
241개가 디스크에 그대로 남아 있지만 분류 대상에서만 빠집니다.

## 🔒 남은 규약

수정 후 재검증했습니다.

```
jsonl 파일: 420개로 늘어남
사용자 세션: 76개 유지  ← 안 늘어남
```

루프가 끊겼습니다. 다만 이건 **구조적으로 안전해진 게 아니라 규약으로 막은 것**입니다.
README에 이렇게 남겼습니다.

> **어디든 새 LLM 호출을 추가하면 `call_claude()`를 통하게 하세요.**
> 이걸 우회하는 호출 하나가 루프를 다시 엽니다.

`call_claude()`를 우회해서 `subprocess.run([CLAUDE, ...])`을 직접 쓰면
그 세션은 기록되지 않고 루프가 부활합니다. 이건 타입으로도 린트로도 못 막습니다.
그래서 문서에 명시적으로 적어뒀습니다.

## 💭 왜 놓쳤나

설계할 때 이걸 전혀 고려하지 않았습니다.

파이프라인을 그릴 때 저는 `~/.claude/projects`를 **읽기 전용 데이터 소스**로 봤습니다.
로그 파일이니까요. 그런데 그 디렉터리는 **내 도구가 쓰기도 하는 곳**이었습니다.

일반화하면 이렇습니다.

> **LLM을 부르는 도구가 LLM 사용 기록을 분석한다면, 출력이 입력으로 되돌아온다.**

비슷한 형태가 꽤 있습니다.

- 커밋 로그를 분석해서 커밋을 만드는 도구
- 이슈를 읽고 이슈를 여는 봇
- 로그를 요약해서 로그를 남기는 서비스
- 테스트 결과를 보고 테스트를 생성하는 파이프라인

전부 같은 함정입니다. **관측 대상과 관측 행위가 같은 저장소를 공유하면** 루프가 생깁니다.

## 📌 정리

- **LLM 호출은 부작용입니다.** 응답만 만드는 게 아니라 로그·세션·과금 기록을 남깁니다
- 그 부작용이 **자기 입력 소스에 쌓이면** 피드백 루프가 됩니다
- 메타데이터 휴리스틱(`entrypoint`, `userType`)으로는 **자식 프로세스를 부모와 구분할 수 없습니다.** 상속되기 때문입니다
- **호출한 쪽이 id를 기록하는 게 유일하게 정확합니다.** 추측하지 말고 응답 봉투에서 받으세요
- 기록은 **응답 직후에** 하세요. 마지막에 몰아 쓰면 중간에 죽었을 때 유실됩니다
- 소급 정리 스크립트는 **dry-run 기본 + 범위 한정**으로 만드세요
- 파일은 지우지 말고 **필터링으로 해결**할 수 있으면 그렇게 하세요. 삭제는 되돌릴 수 없습니다
- 규약으로만 막은 것은 **문서에 명시**하세요. 다음 사람이 우회하면 그대로 재발합니다
