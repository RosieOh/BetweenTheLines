# [블로그 개선] 린트가 6개월 전부터 알려주던 크래시

이 블로그를 처음부터 다시 뜯어보기로 했습니다. 첫 작업은 분석이었고, `npm run lint` 한 번에 18건이 나왔습니다.
그중 10건이 error였는데, 두 줄이 유독 눈에 걸렸습니다.

```
src/pages/PostDetail.tsx
  380:23  error  React Hook "useRef" is called conditionally.
                 React Hooks must be called in the exact same order in every render
  381:3   error  React Hook "useEffect" is called conditionally.
                 React Hooks must be called in the exact same order in every render
```

린트 경고를 방치하면 언젠가 대가를 치른다는 말은 흔합니다.
그런데 이건 "언젠가"가 아니라 **이미 터지고 있는 크래시**였습니다.
다만 재현 조건이 특이해서 아무도 모르고 있었을 뿐입니다.

## 🕰️ 사건 타임라인

- 블로그 전체 분석 착수, `npm run lint` 18건(에러 10) 확인
- `rules-of-hooks` 에러 2건이 같은 파일 같은 위치에 몰려 있는 것을 발견
- 코드를 읽고 "첫 진입에서는 절대 재현되지 않는" 구조임을 파악
- 헤드리스 브라우저로 클라이언트 라우팅 시나리오를 만들어 재현 시도
- 훅 2개를 조기 반환 위로 이동 → 동일 시나리오에서 정상 404 화면 확인

## 🚨 문제

`PostDetail.tsx`의 구조는 이랬습니다.

```tsx
const PostDetail = () => {
  const { id } = useParams();
  const post = allPosts.find((p) => p.id === id);
  const [contactOpen, setContactOpen] = useState(false);
  // ... 여기까지는 훅이 정상적으로 호출됩니다

  if (!post) {
    return <NotFoundInline message="포스트를 찾을 수 없습니다." />;   // ← 373번째 줄
  }

  const headings = extractHeadings(post.content);

  const observerRef = useRef<IntersectionObserver | null>(null);      // ← 380번째 줄
  useEffect(() => {                                                   // ← 381번째 줄
    // 목차 활성화용 IntersectionObserver
  }, [post.id]);
  // ...
```

조기 반환이 **훅 호출보다 위에** 있습니다.
`post`가 없으면 `useRef`와 `useEffect`는 아예 호출되지 않습니다.

React는 훅을 이름이 아니라 **호출 순서**로 식별합니다.
같은 컴포넌트가 어떤 렌더에서는 훅을 8개 호출하고 다음 렌더에서는 6개만 호출하면,
React 입장에서는 슬롯이 어긋난 것이고 곧바로 에러를 던집니다.

## 🧪 재현

여기가 이 버그의 고약한 지점입니다.

**없는 글로 처음부터 들어가면 멀쩡합니다.** 훅을 6개만 호출한 채로 마운트되고, 그대로 끝나기 때문입니다.
문제는 **같은 컴포넌트 인스턴스가 유지된 채로 post가 있다 → 없다로 바뀔 때**입니다.

React Router는 `/post/35`에서 `/post/없는글`로 이동할 때 `PostDetail`을 언마운트하지 않습니다.
`id` 파라미터만 바뀐 같은 라우트이므로 컴포넌트는 재사용되고, 리렌더만 일어납니다.

즉 재현 조건은 이렇습니다.

1. 유효한 글 상세로 진입 (훅 8개 호출)
2. 클라이언트 라우팅으로 존재하지 않는 글로 이동 (훅 6개 호출)
3. 훅 개수 불일치 → 크래시

새로고침으로 접근하면 절대 재현되지 않습니다.
링크를 눌러 이동해야만 나옵니다. QA에서 놓치기 딱 좋은 형태입니다.

## 🔍 원인 분석

근본 원인은 단순합니다. **훅 호출 위에 조건부 반환을 둔 것**입니다.

다만 왜 오래 살아남았는지는 따로 볼 만합니다.

### 1) 린트가 잡고 있었지만 묻혀 있었다

에러 10건, 경고 8건. 그중 6건은 쓰지도 않는 shadcn 컴포넌트에서 나오는 노이즈였습니다.
**진짜 버그 2건이 노이즈 16건 사이에 섞여 있으면 사람은 그걸 구분하지 않습니다.**
"원래 좀 나오는 프로젝트"가 되는 순간 린트는 신호가 아니라 배경음이 됩니다.

### 2) CI가 린트를 돌리지 않았다

배포 워크플로는 `npm run build`만 실행하고 있었습니다.
빌드는 타입 에러가 아니면 통과하고, `rules-of-hooks`는 타입 에러가 아닙니다.

### 3) 재현 조건이 일상 동선과 어긋났다

글을 쓰는 사람은 자기 글 URL로 직접 들어갑니다.
없는 글로 이동하는 건 오래된 링크를 타고 온 방문자 쪽 동선입니다.

## 🛠️ 해결

훅을 전부 조기 반환 위로 올렸습니다.

```tsx
const PostDetail = () => {
  const { id } = useParams();
  const [contactOpen, setContactOpen] = useState(false);
  const [activeId, setActiveId] = useState("");
  const { liked, toggle: toggleLike } = useLike(id ?? "");

  const allPosts = useMemo(() => getAllPosts(), []);
  const post = useMemo(() => allPosts.find((p) => p.id === id), [allPosts, id]);
  const headings = useMemo(() => extractHeadings(content), [content]);

  useEffect(() => { /* 본문 로드 */ }, [post]);
  useEffect(() => { /* SEO 메타 */ }, [post]);
  useEffect(() => { /* IntersectionObserver */ }, [headings]);

  // 모든 훅이 끝난 뒤에 분기합니다
  if (!post) {
    return <NotFoundInline message="포스트를 찾을 수 없습니다." />;
  }
  // ...
```

포인트는 세 가지입니다.

- `post`가 `undefined`여도 훅은 **전부 같은 순서로** 호출됩니다
- 각 `useEffect` 내부에서 `if (!post) return;`으로 방어합니다 — 훅은 호출하되 일은 안 합니다
- `headings`를 `useMemo`로 뽑아 옵저버 훅의 의존성을 안정화했습니다

## ✅ 검증

"고쳤다"로 끝내지 않고 원래 크래시하던 시나리오를 그대로 재현했습니다.
빌드 산출물을 GitHub Pages와 같은 규칙으로 서빙하고, 헤드리스 크롬을 CDP로 몰았습니다.

```
1. 유효한 글 진입      : [StoryG 프로젝트] AI 재생성 불능 이슈 해결기: stale 캐시
2. 다른 글로 SPA 이동  : (정상 렌더)
3. 없는 글로 SPA 이동  : 404 화면 정상
4. 다른 글 직접 진입   : {"highlighted":24,"toc":13,"imgs":3}

콘솔 에러: []
```

3번이 원래 터지던 지점입니다. 콘솔 에러 0건으로 지나갔습니다.

## 🧯 재발 방지

같은 실수를 코드 리뷰로 막을 생각은 하지 않았습니다. 파이프라인을 바꿨습니다.

- **노이즈 제거** — 도달 불가능한 shadcn 컴포넌트 45개를 삭제해 린트 에러 6건이 함께 사라졌습니다
- **린트 0건 상태 확보** — 남은 에러도 전부 정리해 18건 → 0건
- **CI 게이트 추가** — `lint → typecheck → test`를 배포 전에 실행하도록 변경
- **PR 단계 검증** — 배포 워크플로는 `main` 푸시에서만 돌아서 PR이 무검증으로 남던 문제도 함께 해결

린트를 0으로 만드는 진짜 이유는 결벽이 아닙니다.
**0이어야 다음에 1이 뜰 때 그게 신호로 보이기 때문입니다.**

## 📌 정리

- `if (!x) return` 을 훅 위에 두는 순간, 그 컴포넌트는 **리렌더로 x가 사라지는 경로에서만** 터집니다
- 첫 진입에서 재현되지 않는 버그는 새로고침 기반 QA를 그대로 통과합니다
- `react-hooks/rules-of-hooks`는 스타일 규칙이 아니라 **런타임 크래시 예보**입니다
- 린트 에러가 상시 N건인 저장소에서는 N+1이 보이지 않습니다. 0으로 만들어야 경보가 작동합니다
